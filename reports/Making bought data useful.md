# Make every paid step build on the last

Agento's purchases are not useless. The problem is that a run carries out a script written before any data comes back. In `src/server/orchestrator.ts:660-672`, every step whose inputs are ready starts at the same moment. The only link between steps is a mechanical copy of one field into one argument (`src/server/agents/toolbox.ts:440-458`). No model call between steps ever reads what was found and decides what to buy next. So the "thinking" you see at plan time stays in the chat and never reaches the run. The final write-up gets a squeezed, cut-off copy of the answers and no list of questions to answer. That is why reports read like Google results, and the honest answer to "why pay?" has two parts. Part of what Agento buys really is Google: Serper is Google search, in machine-readable form. That only earns its price if the agent does the follow-up reading and cross-checking a person would do, and today it doesn't. Coresignal, PredictLeads and BlockRun do hold data Google cannot show: headcount month by month, dated funding and layoff events, and lists filtered across thousands of companies. Their value appears only when the question is about change over time or a filtered list, and when one source's answer shapes the next call. The fix is one structural change plus a few supporting ones. Add a short reasoning step between paid calls that reads a shared fact ledger and writes the next call's arguments. Before that, write the job's questions up front and pin down exactly which company is meant. After it, have code compute the cross-source numbers and have the report answer each question. Each of these is laid out below, with a worked company check, how to keep costs in check, how to measure usefulness, and what is still unverified.

## The run follows a script written before any data arrived

The core complaint is right, and the code shows why. When a job is approved, the scheduler `executeNowInNet` starts every planned step whose dependencies are met and runs them in parallel (`src/server/orchestrator.ts:660-672`). A step depends on another only if it has a `bind` that points at an earlier result (`src/server/agents/toolbox.ts:162-170`; `src/server/dataflow.ts:46-49`). A step with fixed arguments depends on nothing, so it starts right away. **In business-check run `4edfd404` ("Bay Area Plumbing"), the news step and the complaints search finished at sequence 19 and 26. The Google lookup they should have learned from finished at sequence 33.** They could not have used anything it found.

The binds that do exist are thin. A bind copies one value from a fixed path such as `$s1.found.name` into one whole argument. If the value is a list, it takes item 0. If it is an object, it skips the step. It cuts the value at 300 characters (`toolbox.ts:440-458`). The path syntax has no string templates, no way to combine two facts into one query, and no way to choose among results (`dataflow.ts:37-43, 52-68`). The only model that touches inputs, `map_inputs`, works only on generic "service" steps. It fills only required fields that are still empty, and code rejects any value that does not appear word for word in earlier results (`toolbox.ts:461-469`; `dataflow.ts:198-215`). By design, it cannot write a new query from what was learned. The "Write it up" stage of a question-only job doesn't reason either. `analyse()` turns each step into its summary view and labels it "Data read", with no model call (`toolbox.ts:610-625`).

The search strings are fixed templates, filled once from what you typed. Business-check searches news for `"{business}"` and the web for `"{business} complaints license"` (`src/server/jobs.ts:369-370`), even though step 1 finds the firm's exact name, address, phone and website. Company-deep runs three blind searches: `"{company}"`, `"{company} complaints lawsuit recall"` and `"{company} earnings cash layoffs"` (`jobs.ts:385-387`). None of them reads the company's site or record, which steps 2 and 3 bought. Both of those steps take `results[0].link`, which assumes the first search hit is the official site (`jobs.ts:383-384`). The plumbing run shows the cost. The complaints search returned Better Business Bureau profiles for other plumbers. The firm's own site said "Licensed … since 1995", but no step looked up the licence. **The finished report then told you to "call (415) 668-8000 to ask for their … CSLB license number" and to check it on the state licensing site.** That was the check the paid job had set out to do.

The plan-time thinking you see never makes it into the run. Built-in cards are put together by code with fixed intro text (`jobs.ts:12-16, 262-277`). For jobs built in chat, the planner's notes from free lookups (up to 1,500 characters, `src/server/explore.ts:295, 313-314`) are replayed only into later chat turns (`explore.ts:143-157`). The report prompt reads only the approved one-line `ask` and your first message (`src/server/report.ts:156`). It never reads the plan's reasons, each step's reason, the chat, or the questions the planner drew up. Those questions (`compose.facts`, stored as `run.lanes` with must/should/nice weights) feed only the verdict weighting and conflict labels (`orchestrator.ts:318-320`; `src/server/verdict.ts:11-32`; `report.ts:89`). **The run never learns what it was supposed to find out.**

## Bought answers are cut down three times before anyone reads them

Even a well-chosen purchase loses most of its value before the report sees it. First, `src/server/web-tools.ts` cuts each vendor answer. A web search keeps 6 results with 120-character titles and 240-character snippets, and only the plain result list is read (`web-tools.ts:41-47`). A grep finds no code that reads Google's knowledge panel, answer box or "people also ask" box. The catalog says Serper returns these, so they are paid for and dropped. Page reads keep 2,400 characters (`web-tools.ts:227-233`). Second, each tool's summary view (`stat()`) cuts again: 5 results, 5 stories, 1,600 characters of page text (`src/server/vendor-tools.ts:153-247`). A generic service answer becomes a 700-character string (`vendor-tools.ts:41-44, 283-286`). As far as the audit shows, Coresignal, PredictLeads and Exa have no tool of their own, so their answers would go down this generic path. That is inferred: the audit followed the built-in cards, which use Serper, Tomba and page reads. Third, the report prompt pastes all step views in step order and cuts them at **6,000 characters**, which can stop mid-JSON and always drops the last steps first (`report.ts:136-157`). Meanwhile, an earlier summary call already reads **12,000** characters of the same data, and its output is then overwritten by the report headline (`orchestrator.ts:683-690, 711`). The one-line findings on the job page, which the code-only report and conflict checks also use, are cut at 48 characters (`toolbox.ts:493`; `report.ts:91, 130`).

Some computed numbers are wrong because the inputs behind them were dropped or mixed. In listing run `2b18af5a` (a refurbished EcoFlow DELTA 3 Max at $823.75), the "typical retail" median of $1,059 included bundles: "+ Solar Panel" at $1,199, a "Plus" model at $1,449, and "2 x DELTA 3" at $1,088. The stored "lowest" of $699 is not among the 8 offers kept (`web-tools.ts:96-101`). **The same unit new costs $854 at EcoFlow and Walmart, so the refurbished price is about 3.5% below new, not "well below typical."** Place ratings are averaged from 8 recent reviews, and Google's own overall rating and review count are never read (`web-tools.ts:65-75`).

Fixed code rules then set a floor on the verdict that the model is not allowed to soften. One "bad" signal or two "warn" signals forces at least "be careful" (`report.ts:67-72`). The news rule warns on any headline that matches a red-flag word list, even if the story is about a different firm (`src/server/signals.ts:16, 107-111`). Missing company records warn even for small local firms (`signals.ts:44`). In the plumbing run, a Chapter 11 headline about "a longtime Bay Area plumbing contractor" (not this firm by name) plus a missing record for a small domain produced "be careful". The headline said the firm "shares a headline with a recent Chapter 11 bankruptcy filing". **No step read the article to see which company it was about.**

Finally, everything bought is used once. You cannot ask a follow-up on a finished job: `sendChat` throws "this job is already running" (`orchestrator.ts:346-349`). Results and the purchase cache belong to one run (`src/lib/reducer.ts:76`; `orchestrator.ts:864, 965, 1001`). The knowledge layer stores only order and settlement lessons (`src/server/knowledge.ts:9-151`). Watches and "run again" buy the same data again (`src/server/watches.ts:70-85`; `orchestrator.ts:1704-1716`). Asking "so is the bankruptcy them?" means paying for a new job that cannot see the old answers.

## Paid data beats Google only for change over time and filtered lists

Each vendor sells something different, and the honest verdict differs by vendor. **Coresignal's edge is history.** It has a monthly headcount series on a three-year rolling window (`employees_count_by_month`), breakdowns by country, dated arrivals of new executives (`key_executive_arrivals`), and an object showing open job postings with monthly, quarterly and yearly change (`active_job_postings_count_change`) ([Coresignal release notes, May 2025](https://docs.coresignal.com/release-notes/may-2025); [multi-source company dictionary](https://docs.coresignal.com/company-api/multi-source-company-api/data-dictionary-multi-source-company-api)). It covers 70M+ companies ([Coresignal Company Dataset](https://coresignal.com/company-dataset/)). Google can show today's LinkedIn headcount. It cannot show a 36-month curve or a list like "US fintechs with 50+ staff". **PredictLeads turns scattered news into dated, typed event rows.** Funding rounds come with a normalized dollar amount, round type, investors and source URLs ([PredictLeads API endpoints](https://docs.predictleads.com/v3/api_endpoints)). News events fall into fixed categories such as `decreases_headcount_by`, `hires`, `acquires` and `expands_offices_to` ([categories guide](https://predictleads.com/blog/predictleads-news-event-categories-guide/)). Job openings carry first-seen and last-seen dates ([job openings dataset](https://docs.predictleads.com/v3/data_models/job_openings_dataset)). Its `discover/*` endpoints search across all companies at once. **Exa is a different kind of search engine, not a private database.** It finds pages by description, filters by publication date, can exclude domains, and returns clean page text and highlights in the same call ([Exa search best practices](https://exa.ai/docs/search/best-practices)). Its `/contents` endpoint turns a known URL into clean text for $0.001 (catalog price).

| Source | What Google can't give you | Worth paying vs Google? | Best use in a company check |
|---|---|---|---|
| Coresignal (multi-source, $0.084) | Headcount by month, executive arrivals with dates, change in open job postings, filtered company lists | **Yes** for trend or list questions; **no** for "how big is X" | Headcount curve and hiring trend, read as computed changes |
| PredictLeads ($0.04 per call) | Dated funding with amount and type, categorized news events, job openings with age, cross-company discovery | **Yes**, especially dated history and discovery; marginal for a famous firm's last round | Funding date and amount, layoff, hire and acquisition events since a set date, which roles are open |
| Exa ($0.007 search, $0.001 contents) | Search by description, date-bounded fresh coverage, clean text in one call | **Yes** for discovery and agent-ready text; **no** for simple fact lookups | Reading the source article behind an event; independent press in a date window |
| Serper ($0.002–0.006) | Nothing a person can't see; it is Google in machine form with date and country filters | **Only as automation**; never present it as paid insight | Pinning the entity; dated news and review streams for computed trends |
| Tomba ($0.01) | Email graph, staff count by department, phone carrier and line type | **Partly**: for verification and contacts, not company facts | Cheap identity cross-check |
| MrScraper ($0.0003–0.001) | Page rendering and proxies, not data | **A tool, not data** | Pages Google won't render; snapshots to compare over time |
| BlockRun nano ($0.001–0.005) | Odds filtered by volume and open interest, price history, "smart money" positions | **Yes** for the analytics; raw odds are also free at the exchanges (general knowledge, unverified) | Prediction-market sanity checks |

Prices and Arc-mainnet payability come from the app's own crawled catalog (`.data/agento.db`, table `capabilities`). So does a warning: **most of the stored input formats for these vendors were guessed by AI, and several are wrong.** Coresignal search is listed as taking a free-text `query`, while its documented filters are fields like `industry`, `country` and `employees_count_gte` ([Coresignal search filters](https://docs.coresignal.com/company-api/base-company-api/endpoints/search-filters)). Serper places is listed as requiring a phone number. An agent that trusts these formats will either get an error or pay for an empty answer.

The insight Google cannot copy comes from **combining a time series with a dated event.** Here is the pattern. Take the last funding date from PredictLeads, compare Coresignal headcount at that month with today, and add the quarterly change in open job postings. That yields a judgement like "raised 18 months ago, headcount down 20% since, hiring down 60% this quarter", which suggests money is running short. No single source states that, Google included, and it costs about $0.12. The same logic covers other checks: whether an announced layoff shows up in the headcount data, whether a company is shifting toward sales (the share of sales roles among new openings against new technology and product launches), and whether leadership is unstable (executive arrivals against announced hires and fresh press). These recipes rest on documented fields, but none has been run (see the last section). For the built-in local-business and listing cards, which run mostly on Serper, **the paid value can only be the work a person would otherwise do.** That means reading the bankruptcy article, finding the licence number, and filtering out bundles. That is exactly the work today's runs skip.

## Seven changes, in order, turn purchases into answers

The research systems that work well share one shape. They write the question down as a brief, then loop: search, reflect on each result, refine the next query. They compress what was found into notes and write only at the end. Anthropic's research agents use "interleaved thinking after each tool result" to "evaluate quality, identify gaps, and refine their next query" ([Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)). LangChain's open-source deep researcher pairs a research brief with a reflection tool and an explicit "research complete" stop ([architecture guide](https://dev.to/bolshchikov/open-deep-research-internals-a-step-by-step-architecture-guide-2ibk)). Gemini Deep Research has the model "identify missing information and discrepancies" before each new round of calls ([Gemini overview](https://gemini.google/overview/deep-research/)). Agento has the planner and the writer but not the reflection in between. The changes below add it, in the order that lets each one build on the last.

| Priority | Change | Complaint it fixes | Where it lands | Rough size |
|---|---|---|---|---|
| 0 | Measure a baseline, and stop the report from being starved or misled | "Reports are wrong or shallow" | `report.ts`, `signals.ts`, `web-tools.ts`, `toolbox.ts:493` | Small |
| 1 | Write 3–6 decision questions at plan time; the report answers each | "It doesn't conclude anything" | Planner, `run.lanes`, `report.ts` prompt | Small–medium |
| 2 | A fact ledger: every bought value stored with its source and date | "Later steps can't use earlier ones" | New store beside `run.results` | Medium |
| 3 | Pin the company before buying anything else | Wrong-company risk from `results[0].link` | New step 0; card templates | Small–medium |
| 4 | A "think between paid calls" step with a priced shortlist and spend cap | "Plan-time thinking doesn't happen at run time" | Scheduler loop in `orchestrator.ts`; bind loop in `toolbox.ts` | Medium–large |
| 5 | Cross-source numbers computed in code, plus hand-written query templates per vendor | "It's just what Google says" | New derive module; per-endpoint templates | Medium |
| 6 | Free follow-ups over the ledger, then reuse across jobs | "Bought data is single-use" | `sendChat` gate; cache keyed on the pinned entity | Medium |

### Fix the write-up and the false alarms first

These are small changes that stop the product from misleading anyone while the larger work lands. Give each step its own share of the report's space (for example 6,000 divided by the number of steps, cut inside `viewOf`) instead of one global cut that drops the last steps (`report.ts:136`). Merge or remove the redundant 12,000-character summary call (`orchestrator.ts:683-690`). Pass the plan's reasons and the questions into the prompt. Before the news rule warns, require the business name to appear in the story's title or snippet (`signals.ts:107-111`). Treat a missing company record as neutral when the place lookup found the business (`signals.ts:44`). Store the full finding text and cut it only on screen (`toolbox.ts:493`). Keep Serper's knowledge panel, answer box, `rating` and `ratingCount` (`web-tools.ts:41-47, 65-66`). Drop bundle and multi-pack offers before computing price statistics, and store the offers the statistics came from (`web-tools.ts:96-101`). As a stopgap before the think step, allow templated binds that combine several facts, such as `"{$s1.found.name} {$s1.found.address} contractor license"`. These should be resolved in the bind loop (`toolbox.ts:440-458`) and in the dependency builder (`dataflow.ts:46-49`), so that business-check and company-deep stop searching blind.

### Write the questions before buying anything

At plan time, the planner should turn your goal into 3–6 decision questions, each marked must, should or nice. The `compose.facts` and `run.lanes` structures already hold that weighting. For "Is Acme a safe 12-month vendor?" the questions might be: Is it growing or shrinking? Is it funded, or at risk of running out of money? Is leadership stable? Is there red-flag news? Does it actually sell what it says it does? Show these on the plan card so you can edit them. Gemini uses its plan card the same way, as an editable agreement on scope ([Latent Space](https://latent.space/reading/inventors-deep-research/)). The questions then do three jobs. The think step aims each purchase at an open question. The run stops when every must-question is answered. The report fills one answer box per question. Each box gives an answer of Yes, No, Mixed, **Not found** or **Not searched**, with a confidence level and its reason, evidence chips linked to facts, a "so what" for your decision, and "what would change this answer". "Not found" has to be a real answer. It separates "we looked and it isn't there" from "we ran out of budget", and it makes the next purchase obvious. Public report benchmarks score on insight and instruction-following, not only coverage ([DeepResearch Bench](https://deepresearch-bench.github.io)).

### Give every step's data one shape, the fact ledger

Proven systems don't pass raw vendor output forward. They compress each result into notes that keep the source attached, and the planner reads the notes ([LangChain open_deep_research](https://github.com/langchain-ai/open_deep_research)). Anthropic stores agent outputs outside the conversation and passes lightweight references, to avoid a "game of telephone" ([Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)). For Agento, that means two objects travel between steps. The first is a fact table that is only ever added to. The second is a set of working notes that the think step rewrites after each stage:

```
Fact  { fact_id, entity_id, field, value, unit, as_of,
        source: { vendor, endpoint, call_id, url?, cost_usd },
        method: "api-field" | "llm-extracted" | "derived",
        inputs?: [fact_ids], confidence }

Notes { answered: { q_id: [fact_ids] }, open_questions: [q_id],
        contradictions: [{ fact_a, fact_b, note }],
        next_calls: [{ vendor, endpoint, args, why, est_cost, moves: q_id }],
        spent_usd, remaining_usd }
```

Vendor fields that have a known path, such as a headcount series or a funding amount, should be pulled out by code as `api-field` rows. A model extracts only from free text, like an article, and those rows are marked `llm-extracted`. The report writer sees the ledger and notes, never raw payloads or the 6,000-character dump. Every sentence must cite a `fact_id`. The existing grounding check (`report.ts:160-168`, `grounding.ts`) extends naturally to reject claims with no id, much as Anthropic runs a separate citation pass ([Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)).

### Pin the company before spending on it

Enrichment vendors work in this order: resolve first, then enrich. One cheap call maps a messy input (a name, URL or profile) to a canonical identity with a confidence score. Every later call is keyed on that identity, because enriching an unresolved name "burns credits on the wrong company" ([Crustdata](https://crustdata.com/blog/company-entity-resolution-messy-inputs); [Apify identity resolver](https://apify.com/mambalabs/company-identity-resolver)). In Agento, step 0 should produce `entity = { canonical_domain, name, coresignal_id?, linkedin_url?, match_confidence, alternatives[] }`. If confidence is low, or the top two candidates are close ("Acme Inc, Berlin" against "Acme Corp, Ohio"), the job pauses with a picker that asks "Which Acme did you mean?" before it spends anything. Every later step takes the pinned domain or ID, replacing `results[0].link`. When the domains agree across Coresignal, PredictLeads and Exa, that agreement goes into the ledger as an identity-confirmation fact. A mismatch is a contradiction to show you.

### Add a think step between paid calls, with a priced shortlist

This is the change that answers the main complaint. Group the plan's steps into stages, such as pin, then core data, then events, then verification. Calls within a stage still run in parallel. After each stage, run one model call. It reads the brief, the questions, the ledger, the remaining budget and a menu of hand-written vendor query templates. It returns one of four choices: the typed arguments for the next calls, "skip", "stop, all must-questions answered", or "ask the user". Unlike `map_inputs`, it may *compose* a query from facts it has bought, for example a domain plus "layoffs" plus a date window. The entity arguments (domain or IDs) still have to come from the pin, and every call has to match a vetted template. That keeps today's protection against made-up inputs without its rigidity.

Cost control lives inside the think step. Each proposed call carries an estimated cost and the question it could change. The rule is to **buy it only if it can move a question that is open or low-confidence**. Researchers found that a bigger tool budget does not by itself improve an agent. Making the agent aware of its remaining budget kept accuracy the same with **40.4% fewer search calls and a 31.3% lower overall cost** ([VentureBeat on BATS](https://venturebeat.com/ai/googles-new-framework-helps-ai-agents-spend-their-compute-and-tool-budget); [arXiv 2511.17006](https://arxiv.org/abs/2511.17006v1)). Within each question, try the cheapest source first, in this order: facts already in the ledger, then cheap structured sources, then search. This is the "waterfall" enrichment tools use ([Clay](https://www.clay.com/guides/waterfall-enrichment)). The approved plan sets a spend ceiling with a small reserve. Re-plans that stay under it run on their own. Anything above it, or a new vendor, goes back to you with a reason in plain words, for example "Headcount fell 22%. Spend $0.04 more on news to find out why?". That fits the existing approval and passkey flow. Set a hard cap on think rounds (three is plenty for a company check) as a guardrail. Anthropic's early agents launched 50 sub-agents for simple questions ([Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)).

### Compute cross-source numbers in code, and query each vendor properly

Do the joining and arithmetic in code, and let the model explain the results. STORM's authors name "over-association of unrelated facts" as a failure mode of model-written summaries ([STORM](https://storm-project.stanford.edu/research/storm/)), and Agento's own number check already distrusts model arithmetic. A small derive module should write `derived` facts that point back to their inputs:

- headcount change over 6 and 12 months, and since the last funding month
- open jobs as a share of headcount
- the sales share of roles first seen in the last 60 days
- months since the last raise
- a merged, dated timeline of events
- domain and headquarters agreement across sources
- recent review rating against the lifetime rating

Each vendor endpoint also needs a hand-written query template to replace the guessed formats in the catalog. Every template should be date-bounded (`first_seen_at_from`, `startPublishedDate`, `tbs`, `created_at_gte`), because an undated pull pays for stale rows. Buy lists cheaply and buy depth only for the shortlist: a Coresignal search costs $0.021, while a multi-source record costs $0.084. And show "what Google would have told you" next to "what the paid data added". That box answers "why pay?" on every report.

### Answer follow-ups from what you already bought

Open finished jobs to a follow-up chat that answers **from the ledger first, for free**. It cites the old facts with their as-of dates, and offers to buy only the missing pieces, with prices shown. Today that is blocked at `orchestrator.ts:346-349`. Next, key a cache on `(vendor, endpoint, pinned entity, normalized arguments)`, with a freshness window per data type. Headcount can stay valid for about a month, news for a few days. That way a new job, a watch or "run again" reuses fresh answers instead of buying them again. The leftover `learned_recipes` table and the shared-knowledge-layer work are natural homes for this. Before reusing data across different users, check the vendors' licence terms on caching. Those terms were not researched.

### Measure usefulness, starting before the first change

Pick about 20 real checks: companies, local businesses and listings. Anthropic found that a set that size reveals large effects ([Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)). Score each run from 0 to 1 on five points, using a model as judge plus a human spot-check:

1. Is every question answered, or marked not found?
2. Does every claim cite a fact that supports it? (This is a cheap check, because the facts are already structured.)
3. Is it the right entity?
4. Is there at least one finding that no single vendor response contains?
5. Is spending efficient: dollars per answered question, and the share of paid calls that changed an answer?

The fifth measure is the paid-data version of Anthropic's "tool efficiency" score, and it measures "bought data made useful" directly. Run the set before any change, as a baseline, and again after each priority level. Human testers matter too: Anthropic's testers caught agents preferring SEO content farms over authoritative sources.

## One company check, traced dollar by dollar

Here is how "Check Acme (acme.io): Coresignal → PredictLeads → Exa → summary" should run. The company and its numbers are illustrative, not real purchases. The field names follow the vendors' public documentation, with the caveats in the next section. Today, company-deep would run three searches for the bare name in parallel, read whatever page ranked first, and hand a squeezed copy of the results to the writer.

The total spend is about **$0.21**, plus the model's reasoning calls. That is close to the notes' estimate of $0.20 for a full company dossier. ## What these findings rest on, and what is still unverified

The code findings come from reading the repository and from read-only queries of the app's database: runs `4edfd404` and `2b18af5a`, and the `capabilities` table. A few points are inferred, not observed. One is that a delivered page read would push the plumbing run past the 6,000-character cut and drop the news and complaints steps. Another is that Coresignal, PredictLeads and Exa answers go through the 700-character generic path. A third is that the listing rule's wording changed since that run. The audit did not confirm whether chat-built jobs ever use the conditional (`when`) or verify options the schema allows (`src/server/tools.ts:457-476`).

The vendor facts are weaker. **The documentation sites for Coresignal, PredictLeads and Exa could not be reached from this sandbox.** Their details come from search-engine summaries of those official pages and from the app's catalog. **No paid calls were made.** These points are unconfirmed:

- the exact field names for executive departures, funding and revenue in Coresignal's multi-source data
- whether the cheaper Coresignal tiers carry the monthly series
- whether Orthogonal passes Coresignal's search body and PredictLeads' filters through unchanged
- whether PredictLeads' date filter works on news events, and what its category parameter is called
- whether Exa's $0.007 price covers summaries and fresh crawls
- the parameter names for Serper reviews, which come from a third-party wrapper

Vendor sources also disagree among themselves. Coresignal's job-posting count is given as 486M to 580M, and PredictLeads' category count as anywhere from 28 to 46. The hit rates that matter most for a small-company product are unknown: how often PredictLeads has a funding event for a typical small firm, and how complete Coresignal's monthly series is below about 50 staff. The budget-control figures (40.4%, 31.3%) come from press coverage and abstracts, not the full paper. The fact-ledger schema and the decision-card format are a synthesis of the cited systems, not a published standard.

One small test would settle most of this: **about $1, spent with your explicit go-ahead, on 5 known companies across Coresignal and PredictLeads.** It would confirm the field names, the input formats through Orthogonal, and the hit rates before these vendors are featured. Under the project rules, that spend must never come from tests.

## Conclusion

The gap is not between cheap and expensive data. It is between a run that *executes* and a run that *investigates*. Agento already has most of the parts an investigating agent needs: a planner, typed vendor tools, binds, a grounding check, approval gates and a catalog with prices. What's missing is about one model call per stage, plus a shared place to keep what was learned. Adding that changes the product's pitch. "Why pay when you can Google it?" stops being a hard question, because the report shows, question by question, what the purchase found that Google didn't. It also shows what each answer cost.

The order matters more than the size of any single change. Questions come first, because without them the think step has nothing to aim at and no way to know when to stop. The ledger comes next, because without it follow-ups and reuse have nothing to draw on. Pinning comes before any of these purchases, because every dollar spent on the wrong company is lost. Running the 20-check baseline now, before any change, is the only way to show later that the fixes made bought data more useful rather than just more expensive.
